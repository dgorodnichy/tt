# Тренажёр 01. Интерфейсы: вакансия, кандидат, отдел кадров

Не задача проекта и не ревью на оценку. Цель одна — чтобы схема «интерфейс → реализация → сборка» стала автоматической, как `each` в Ruby.

Делается **вне проекта**, в отдельном каталоге:

```
mkdir -p ~/go-drills/interfaces && cd ~/go-drills/interfaces
go mod init drills
```

Каждый раунд — один пакет-каталог, один файл кода и один файл теста. Раунд занимает 10–20 минут. Если раунд пошёл тяжело — повтори его с нуля на следующий день, не подглядывая.

## Главный приём: сначала пользование, потом код

Не нужно держать в голове порядок «структура → методы → конструктор». Порядок задаёт компилятор:

1. **Пишешь тест** — три строки «как я хочу этим пользоваться» и одну проверку. Тест не собирается — так и задумано.
2. **Запускаешь `go test ./...`.** Компилятор называет **первое**, чего не хватает: `undefined: ...`.
3. **Дописываешь ровно это** — минимально, только чтобы ушла эта ошибка.
4. Повторяешь 2–3, пока тест не станет зелёным.

В голове в каждый момент — одна ошибка компилятора, а не вся схема. Когда дойдёшь до параметра конструктора сценария, спроси себя: «что сценарию нужно уметь от того, что ему дали?» — ответ и есть вакансия-интерфейс.

## Модель, которую тренируем

| Роль | В жизни | В Go | Кто пишет | Имя отвечает на вопрос |
|---|---|---|---|---|
| Вакансия | «Требуется: умеет готовить кофе» | интерфейс | тот, кто нанимает (сценарий) | **что умеет?** → `CoffeeMaker` |
| Кандидат | человек со своими навыками | структура с методами | адаптер, ничего не зная о вакансии | **где/как работает?** → `memory.Fridge` |
| Работодатель | кафе, которому нужен бариста | сценарий | пакет `usecase` | **что делает?** → `ServeLatte` |
| Отдел кадров | приводит кандидата в кафе | `main` или тест | точка сборки | — |

Три правила-мнемоники:

1. **Вакансию пишет работодатель, а не кандидат.** Интерфейс объявляется там, где им пользуются.
2. **В вакансии — только то, что понадобится на работе.** Один-два метода, не все умения кандидата.
3. **Кандидат не читает вакансий.** У структуры нигде не написано, под какой интерфейс она подходит. Совпадение проверяет компилятор на собеседовании — в момент, когда кандидата отдают в конструктор.

## Карточка перед кодом

Перед каждым раундом (кроме первого — там образец) заполни четыре строки — словами, в комментарии в начале файла. Код пишется только после карточки.

```
// Умение:      что сценарию нужно от внешнего мира (одним глаголом)
// Вакансия:    имя интерфейса и его метод
// Кандидат:    тип, у которого этот метод есть
// Собеседование: строка, где кандидата отдают в конструктор сценария
```

## Правила имён

- Интерфейс — **по умению**: существительное + глагол-деятель. `MilkGiver`, `BookFinder`, `ParcelSaver`. Как в стандартной библиотеке: `io.Reader`, `io.Writer`, `fmt.Stringer`. Не `IMilk`, не `MilkInterface`, не `MilkRepo`.
- Поле сценария — **по роли**, маленькими буквами: `giver MilkGiver`, `finder BookFinder`. Тогда вызов читается как фраза: `s.finder.Find(code)`.
- Сценарий — **по действию**: `ServeLatte`, `LendBook`.
- Кандидат — **по тому, что он такое**: `Fridge`, `Shelf`. Пакет подсказывает, где он живёт: `memory.Shelf`.

## Сборка — всегда три строки

```go
shelf := memory.NewShelf()  // 1. нанять кандидата
lend := NewLendBook(shelf)  // 2. отдать работодателю — здесь собеседование
lend.Call("b-42")           // 3. работать
```

Работодатель никогда не нанимает сам (`NewShelf` внутри сценария не вызывается). Кандидата всегда приводят снаружи.

## Раунд 1. Кофейня

Сценарий «подать латте»: берёт 200 мл молока и возвращает ошибку, если молока не хватило.

Холодильник — это хранилище, как твой `memory.Repo`, только проще: внутри не `map`, а **одно число** — сколько миллилитров молока осталось.

Карточка для этого раунда уже заполнена — как образец:

```
// Умение:        дать молоко
// Вакансия:      MilkGiver, метод GiveMilk(ml int) error
// Кандидат:      fridge.Fridge — внутри число; GiveMilk вычитает или возвращает ошибку «мало молока»
// Собеседование: в тесте latte — latte.NewServeLatte(f), где f — холодильник
```

**Шаг 1. Только холодильник.** Каталог `fridge/`. Тип с одним полем-числом, конструктор с начальным количеством, метод `GiveMilk`, ошибка-переменная «мало молока». Тест: было 500, взяли 200 — ошибки нет; было 100, взяли 200 — ошибка. Это та же форма, что у проекта в задачах 02–03, только поле — число. Ни интерфейсов, ни кофейни здесь ещё нет.

**Шаг 2. Кофейня.** Каталог `latte/`. Вакансия `MilkGiver` из карточки, сценарий с полем этого типа, конструктор, метод «подать», который просит у поля 200 мл и возвращает ошибку как есть.

**Шаг 3. Тест кофейни** в `latte/`: отдел кадров в три строки — создать холодильник, отдать в конструктор кофейни, подать латте.

- В холодильнике 500 — латте подано, ошибки нет.
- В холодильнике 100 — ошибка «мало молока» через `errors.Is`.

## Раунд 2. Библиотека

Сценарий «выдать книгу»: находит книгу по коду; если нет — возвращает ошибку полки как есть.

- Кандидат: полка с `map` внутри.
- Тест: книга есть — выдана; книги нет — ошибка через `errors.Is`.

Сначала карточка. Обрати внимание: умение здесь другое, значит, и вакансия другая.

## Раунд 3. Подмена кандидата

Вернись в кофейню. Напиши **второго** кандидата на ту же вакансию: «пустой холодильник», который всегда отказывает. Прямо в файле теста `latte/`, на три-четыре строки.

- Тест: с пустым холодильником латте не подано.
- Проверь: файл сценария при этом не изменился ни на символ.

Это и есть смысл интерфейса: работодателю всё равно, кто пришёл, лишь бы умел.

## Как понять, что усвоено

Открой пустой файл и за пять минут без подглядывания напиши карточку и сборку в три строки для придуманного тобой сюжета (например, «почтальон отправляет письмо через почтовый ящик»). Получилось — возвращайся к задаче 09.
