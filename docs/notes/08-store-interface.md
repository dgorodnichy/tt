# Конспект к задаче 08. Интерфейс хранилища

Пополняется по ходу задачи: сюда записывается всё, что ты спросил и что мы выяснили.

## В каком файле объявлять интерфейс

Для компилятора это неважно: пакет — это каталог, и все его файлы видят друг друга как один файл (та же мысль, что в «Как назвать файл в пакете» из конспекта 06).

Обычно в Go интерфейс кладут рядом с тем, кто им пользуется: в тот же файл, прямо над типом, у которого поле этого интерфейса. Читатель видит и тип, и то, что ему нужно, в одном месте.

```go
// packer.go
type ParcelKeeper interface {
	Put(p *Parcel)
}

type Packer struct {
	keeper ParcelKeeper
}
```

В отдельный файл интерфейс переносят, когда им пользуются несколько типов пакета, — тогда у него нет одного «хозяина».

В Rails ближайшее — модуль-концерн, который лежит рядом с единственной моделью, пока его не начали подключать в другие.

## Редактор говорит одно, компилятор — другое

Подсказки в редакторе (`Diagnostics`, красные подчёркивания) даёт отдельная программа — языковой сервер `gopls`. Она иногда сбивается после правок: не успевает перечитать другой пакет и показывает ошибки, которых нет.

Признак сбоя — слово `invalid type` в сообщении: редактор сам не смог понять тип и сдался. Настоящий судья — компилятор:

```
go build ./...
go vet ./...
```

Если они молчат, а редактор ругается, — перезапустить языковой сервер (или редактор целиком).

В Rails похоже на ситуацию, когда Solargraph или RuboCop в редакторе подсвечивает ошибку, а `rspec` проходит.

## Где компилятор ругается, если тип не подходит под интерфейс

Ошибка появляется не там, где объявлен тип, а там, где его **пытаются отдать** вместо интерфейса.

```
packer_test.go:14:43: cannot use shelf (variable of type *store.Shelf) as ParcelKeeper value
in argument to NewPacker: *store.Shelf does not implement ParcelKeeper (missing method Put)
```

Сам `Shelf` ни в чём не виноват: он не обещал быть `ParcelKeeper`, значит, и нарушать нечего. Проверка случается в момент встречи — когда полку передают туда, где ждут «что-нибудь с `Put`». Конец сообщения называет, какого метода не хватило.

В Ruby в такой ситуации ничего не случилось бы до вызова, а потом — `NoMethodError` во время работы.

## `http.Handler` — интерфейс из твоего первого `main.go`

`go doc net/http.Handler`:

```go
type Handler interface {
	ServeHTTP(ResponseWriter, *Request)
}
```

`http.ListenAndServe(addr, handler)` принимает любой тип с методом `ServeHTTP`. `*http.ServeMux` нигде не пишет, что он `Handler`, — у него просто есть такой метод. Ровно как твой `*memory.Repo` и `ProjectsRepo`.

`http.HandlerFunc`, который в задаче 01 ты назвал интерфейсом, — не интерфейс, а тип-функция, у которой есть метод `ServeHTTP`. Поэтому она тоже подходит под `Handler`. Интерфейс — это список требований; `HandlerFunc` и `ServeMux` — два разных типа, которые им удовлетворяют.
