# Конспект к задаче 05. Идентификатор проекта

Пополняется по ходу задачи: сюда записывается всё, что ты спросил и что мы выяснили.

## `not enough arguments in call to ...`

Так компилятор говорит: функцию вызвали не с тем числом аргументов.

```
internal/store/parcel_test.go:29:36: not enough arguments in call to NewParcel
	have (string)
	want (string, int)
```

Как читать:

- `parcel_test.go:29:36` — файл, строка, позиция в строке.
- `have` — что передано в вызове сейчас (типы аргументов).
- `want` — что функция ждёт по своему объявлению.

Сравнил две строки — видно, какого аргумента не хватает и на каком месте.

Таких блоков в выводе столько, сколько старых вызовов осталось в коде. Каждый блок — отдельное место, чинить нужно все. Это и есть польза: после смены параметров функции искать вызовы глазами не надо, компилятор перечислит их сам.

В Ruby то же самое выглядит как `ArgumentError: wrong number of arguments (given 1, expected 2)`, но приходит только тогда, когда выполнение дойдёт до вызова.

## `%q` вместо `%v` для строк в сообщениях

`%v` печатает строку как есть, и пустую строку в сообщении не видно. `%q` печатает её в кавычках.

```go
t.Errorf("got code %v, want %v", "", "A1") // got code , want A1
t.Errorf("got code %q, want %q", "", "A1") // got code "", want "A1"
```

В кавычках видны и пустая строка, и пробелы по краям, и перенос строки (`"A1\n"`). Для строк в сообщениях тестов `%q` почти всегда лучше.

В Ruby это разница между `puts s` и `p s` (или `s.inspect`).

## Неизменяемое поле: нет метода — нет способа изменить

В Go нет слова вроде `readonly` для поля. Неизменяемость делается проще: поле с маленькой буквы, метод чтения есть, метода изменения нет. Снаружи пакета поменять значение нечем.

```go
func (p *Parcel) Code() string { return p.code } // читать можно
// SetCode не существует — значит, код посылки не меняется никогда
```

Каждый лишний метод с большой буквы — это обещание, что так делать можно. Метод изменения «на всякий случай» ломает правило, ради которого поле прятали.

В Ruby это `attr_reader :code` без `attr_writer`.

## Правило должно быть одно и то же везде, где оно применяется

Если проверка считает значение пустым после обрезки пробелов, а сохраняется значение необрезанным, то в объект попадает `" A1 "` с пробелами — проверка смотрела на одно, а сохранили другое. Либо обрезаем и проверяем обрезанное (как с названием), либо не обрезаем вообще.

## `gofmt -l .` печатает имена файлов

Пустой вывод — всё отформатировано. Если напечатано имя файла, в нём есть неотформатированные строки (лишние пробелы в конце, неровные отступы). `gofmt -d файл` покажет, что именно не так; `gofmt -w файл` исправит. Лучше один раз включить форматирование при сохранении в редакторе.

## Та же ловушка третий раз: поле «что ждём» заведено, а сравнение идёт с полем «что подали»

Если в таблице есть пара `code` / `wantCode`, а в цикле написано `got.Code() != tt.code`, то `wantCode` никто не читает, и в него можно вписать что угодно. Проверка та же, что и раньше: вписать в `want…` неверное значение и посмотреть, покраснеет ли тест.

## Метод, который всегда отказывает, или метода нет

Запретить действие можно двумя способами.

- Написать метод, который проверяет и возвращает ошибку. О запрете узнают, когда программа уже работает и дошла до этого вызова.
- Не писать метод. Тогда вызов не соберётся: `p.SetCode undefined`. О запрете узнают сразу, от компилятора.

```go
// способ 1: отказ во время работы
func (p *Parcel) SetCode(code string) error { return ErrImmutableCode }

// способ 2: метода нет вообще — писать нечего
```

Если действие запрещено всегда, без исключений, в Go выбирают второй способ. Проверка, которая никогда не пропускает, — это код, который нужно читать, тестировать и поддерживать, а пользы от него меньше, чем от его отсутствия.

Признак: у обычного метода есть два вида тестов — где он **сработал** (вернул `nil`, значение изменилось) и где **отказал**. Если для правильно созданного объекта можно написать только тест на отказ, метод ничего не умеет, кроме как отказывать, — он лишний.

В Rails привычен первый способ (`attr_readonly`, `raise` в сеттере): там компилятора нет, и отказ во время работы — единственный вариант.

## Закомментированный код

Строку, которая больше не нужна, удаляют, а не комментируют. Она останется в истории `git`, и достать её оттуда можно всегда. Закомментированный код в файле читатель вынужден прочитать и гадать, зачем он оставлен.
