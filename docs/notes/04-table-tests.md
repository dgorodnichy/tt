# Конспект к задаче 04. Табличные тесты

Пополняется по ходу задачи: сюда записывается всё, что ты спросил и что мы выяснили.

## `errors.Is`, когда ошибки нет

`errors.Is(err, want)` отвечает на вопрос «это та самая ошибка?». `nil` здесь — обычное значение «ошибки нет», и оно тоже сравнивается.

```go
errors.Is(nil, nil)               // true  — не ждали ошибку и не получили
errors.Is(nil, ErrNegativeWeight) // false — ждали ошибку, а её нет
errors.Is(ErrNegativeWeight, nil) // false — не ждали, а она пришла
```

Поэтому одна проверка `if !errors.Is(err, tt.wantErr)` покрывает сразу оба вида случаев в таблице: и успешные (в поле ожидаемой ошибки `nil`), и с ошибкой. Сработает ли `if`, зависит не от одного `err`, а от пары «что пришло» и «что ждали».

В RSpec это как `expect(result).to eq(expected)`, где `expected` может быть и `nil`.

## Падает строка таблицы: подставь её в цикл руками

В сообщении о падении стоит номер строки с `t.Fatalf` внутри цикла, а не строки таблицы. Ошибка при этом может быть и в таблице, и в теле цикла.

Способ найти: взять упавшую строку таблицы и пройти тело цикла сверху вниз, подставляя вместо `tt.поле` настоящие значения из этой строки. На каком-то шаге станет видно, что в функцию уходит не то, что задумано.

```go
{name: "отрицательный вес", weight: -1, wantWeight: 5, wantErr: ErrNegativeWeight},
...
err := parcel.SetWeight(tt.wantWeight) // подставляем: SetWeight(5) — а хотели -1
```

У таблицы есть своя ловушка: поля «что подаём» и «что ждём» называются похоже, и перепутать их в теле цикла легко. Компилятор не поможет — типы совпадают.

Часть строк при такой путанице проходит **случайно**: если «подаём» и «ждём» в строке совпали, ошибка не видна. Зелёная строка таблицы ещё не значит, что цикл написан верно.

## Имя случая в `t.Run` и запуск одного случая

Первый аргумент `t.Run` — это имя, которое попадёт в вывод и по которому случай можно запустить отдельно. Что туда передал, то и увидишь.

```go
t.Run(tt.input, ...)  // в выводе: TestBox/aaaaaaaaaaaa, TestBox/#00, TestBox/___
t.Run(tt.title, ...)  // в выводе: TestBox/пустой_вес
```

Что Go делает с именем сам:

- пробелы заменяет на `_`;
- пустое имя превращает в `#00`, `#01`;
- одинаковые имена различает добавкой `#01`.

Запуск одного случая — имя функции, косая черта, имя случая:

```
go test ./internal/store -v -run 'TestBox/пустой вес'
```

Пробелы и кириллица в команде работают: Go сам заменит пробелы на `_` перед сравнением. Если в ответ пришло `no tests to run`, значит, случая с таким именем нет — смотри в выводе `-v`, как он называется на самом деле.

В RSpec это `rspec -e "пустой вес"`.

## Поле таблицы, которое никто не читает

Компилятор не проверяет, что поле структуры где-то используется. Поле может быть заполнено в каждой строке таблицы и ни разу не прочитано в цикле — всё соберётся и будет зелёным.

Отсюда же вторая ловушка: ранний `return` после ожидаемой ошибки. Всё, что стоит в цикле ниже него, для строк с ошибкой не выполняется. Если в такой строке записано «что ждём после отказа», эта запись — просто текст, проверки за ней нет.

Проверка: впиши в поле заведомо неверное значение. Тест остался зелёным — поле не проверяется.

## `Fatalf` или `Errorf` между двумя проверками

`Fatalf` ставят, когда дальше идти не с чем: объекта нет, следующая строка упадёт. Если объект есть и проверяются два его независимых поля, между проверками лучше `Errorf`: при ошибке в первом поле ты всё равно узнаешь, что со вторым.

```go
if got.Weight() != tt.wantWeight {
	t.Errorf("got weight %d, want %d", got.Weight(), tt.wantWeight) // идём дальше
}
if got.Code() != tt.wantCode {
	t.Errorf("got code %q, want %q", got.Code(), tt.wantCode)
}
```

С `Fatalf` в первой проверке вторая не выполнится, и вторую ошибку ты увидишь только после того, как починишь первую.
