# Конспект к задаче 06. Хранилище проектов в памяти

Пополняется по ходу задачи: сюда записывается всё, что ты спросил и что мы выяснили.

## Как назвать файл в пакете

Go не смотрит на имя файла. Пакет — это каталог, и все файлы в нём видят друг друга, как будто это один файл. Имя выбирают для людей: по тому, что лежит внутри, маленькими буквами, слова через `_`.

```
internal/store/shelf.go       // тип Shelf и его методы
internal/store/shelf_test.go  // тесты к нему
```

Единственное имя, которое Go понимает сам, — окончание `_test.go`.

В Rails имя файла обязано совпадать с именем класса, иначе автозагрузка его не найдёт. В Go такого правила нет.

## Хранилище устроено так же, как проект

Форма одна и та же: тип с закрытым полем, конструктор, методы. В проекте поле — строка, в хранилище — `map`. Больше отличий нет.

```go
type Shelf struct {
	items map[string]int
}

func NewShelf() *Shelf {
	return &Shelf{items: make(map[string]int)}
}

func (s *Shelf) Put(name string, count int) {
	s.items[name] = count
}
```

`map` создаётся внутри конструктора. Снаружи его не передают: тогда тот, кто его создал, мог бы менять содержимое в обход методов, и закрытое поле потеряло бы смысл.

В Ruby это класс, у которого в `initialize` стоит `@items = {}`, а дальше обычные методы.

## Откуда метод берёт `map`: получатель

Обычная функция видит только свои параметры. Поэтому в `func Put(name string, count int)` никакого `items` нет, и возникает желание передать `map` ещё одним параметром.

Метод отличается одним: перед именем в скобках стоит получатель — объект, у которого метод вызвали. Через него метод достаёт поля.

```go
func Put(items map[string]int, name string, count int) // функция: map приходится передавать
func (s *Shelf) Put(name string, count int)             // метод: map лежит в s.items
```

Вызов тоже разный: `Put(m, "apple", 3)` против `shelf.Put("apple", 3)`.

Это тот же приём, что в методе смены названия у проекта: там получатель `p`, и поле достаётся как `p.поле`.

В Ruby получатель — это `self`, только там он появляется сам, а в Go его пишут явно и дают ему имя.

## `non-name ... on left side of :=`

`:=` заводит **новую переменную**, поэтому слева от него может стоять только имя. Ячейка в `map` — не новая переменная, а место в уже существующей вещи. Туда пишут обычным `=`.

```go
count := 3            // новая переменная count
stock["apple"] = 3    // запись в существующий map
stock["apple"] := 3   // ошибка: non-name stock["apple"] on left side of :=
```

То же самое с полем: `p.weight = 5`, а не `p.weight := 5`.

## `cannot use ... as ... value`: тип со звёздочкой и без — разные типы

`Parcel` и `*Parcel` для компилятора — два разных типа, один вместо другого не подставляется. Сообщение читается так: «нельзя использовать то-то (типа А) как значение типа Б».

```
cannot use s.items[id] (map index expression of struct type Parcel) as *Parcel value in return statement
```

Здесь в `map` лежит `Parcel`, а метод обещал вернуть `*Parcel`. Лечится тем, что тип пишут одинаково в трёх местах: что отдаёт конструктор, что лежит в `map`, что возвращает метод. Отправная точка — конструктор: что он отдаёт, то и хранят.

## Хранилище хранит, а не создаёт

Метод «сохранить» принимает **готовый** объект. Создаёт его кто-то другой — конструктором, заранее.

```go
parcel, err := NewParcel(5) // создал — здесь проверяются правила
shelf.Put(parcel)           // положил — здесь проверять уже нечего
```

Отсюда следствие: у «сохранить» в память нечему пойти не так, и `error` в результате ему не нужен (та же запись, что в конспекте 03: ошибку возвращает тот, у кого что-то может не получиться).

В Rails `Parcel.create(weight: 5)` делает оба шага сразу: и создаёт, и сохраняет. Здесь это два разных действия в двух разных местах.

## `panic: assignment to entry in nil map`

Объявить поле с типом `map` — ещё не значит создать `map`. Пока его не создали через `make`, в поле лежит `nil`. Читать из такого `map` можно (вернётся пустое значение), а запись роняет программу.

```go
type Shelf struct {
	items map[string]int
}

s := &Shelf{}          // items == nil
n := s.items["apple"]  // работает: n == 0
s.items["apple"] = 3   // panic: assignment to entry in nil map
```

Создают `map` в конструкторе — так, как в `NewShelf` из задачи.

В Ruby то же самое случается, если в `initialize` забыть `@items = {}`: `@items` равен `nil`, и `@items["apple"] = 3` падает с `NoMethodError`.

## Как читать панику

Вывод паники — это тот же backtrace, что в Rails, только с шумом. Читать в четыре шага.

**1. Первая строка `--- FAIL` — какой тест.**

**2. Строка `panic:` — что случилось.** Самые частые:

- `assignment to entry in nil map` — запись в `map`, который не создан через `make`;
- `invalid memory address or nil pointer dereference` — вызвали метод или взяли поле у `nil`. В Ruby это `NoMethodError: undefined method 'weight' for nil`.

Строку `[signal SIGSEGV ...]` под ней пропускаем — это то же самое на языке операционной системы.

**3. Вычеркнуть чужое.** Всё, где путь ведёт в `/libexec/src/` или имя начинается с `testing.`, `panic(`, `runtime.`, — внутренности Go. Строки `goroutine 4 [running]` и `created by ...` тоже пропускаем.

**4. Оставшиеся строки идут парами: функция, под ней `файл:строка`.** Верхняя пара — где упало, следующая — кто её вызвал. Порядок как в Ruby: сверху — место ошибки, ниже — цепочка вызовов.

```
panic: runtime error: invalid memory address or nil pointer dereference
example.com/shop/internal/store.(*Parcel).Weight(...)
	/home/me/shop/internal/store/parcel.go:26        ← упало здесь
example.com/shop/internal/packing.TestPackEmpty(...)
	/home/me/shop/internal/packing/packing_test.go:50 ← а вызвали отсюда
```

Важно: верхняя строка — где `nil` **использовали**, а не где он появился. Метод `Weight` написан правильно, он просто получил `nil`. Ищи причину на строку ниже — в том, кто этот `nil` передал. В Ruby так же: `NoMethodError` указывает на строку с `.weight`, а виноват тот, кто положил `nil` в переменную.

## `nil` бывает не у всякого типа

В Ruby любая переменная может быть `nil`. В Go — нет. Тип без звёздочки `nil` не бывает никогда: там всегда лежит значение, в крайнем случае «пустое» (все строки `""`, все числа `0`). Тип со звёздочкой бывает `nil`.

```go
var a Parcel  // пустая посылка: вес 0, код "". Не nil
var b *Parcel // nil — посылки нет

a == nil // ошибка: mismatched types Parcel and untyped nil
b == nil // true
```

Отсюда два сообщения компилятора:

```
invalid operation: s.items[id] == nil (mismatched types Parcel and untyped nil)
cannot use nil as Parcel value in return statement
```

Оба говорят одно: «у этого типа `nil` не бывает». Поэтому конструктор, который при отказе отдаёт `nil`, возвращает тип со звёздочкой. И всё, что хочет уметь сказать «объекта нет», — тоже.

Есть ли ключ в `map`, спрашивают не сравнением с `nil`, а вторым значением:

```go
n, ok := stock["pear"] // ok == false — ключа нет
```

## `error.New undefined`

`error` (без `s`) — это тип, им пишут «функция возвращает ошибку». `errors` (с `s`) — пакет, в нём лежит функция `New`. Пакет нужно импортировать.

```go
import "errors"

var ErrEmptyShelf = errors.New("empty shelf")

func (s *Shelf) Take() error { ... }
```

## `%q` — для строк, `%v` — для ошибок

`%q` берёт строку в кавычки, чтобы были видны пробелы и пустота. Ошибку печатают через `%v`: кавычки ей не нужны, а если ошибки нет, `%q` напечатает мусор.

```go
t.Errorf("got name %q, want %q", got, want) // got name "", want "box"
t.Errorf("got error %v, want %v", err, want) // got error <nil>, want empty shelf
t.Errorf("got error %q", err)                // при err == nil: got error %!q(<nil>)
```

## Создать объект — не значит положить его в хранилище

Конструктор только создаёт объект в памяти. В хранилище он попадает, когда его туда положили. Если результат конструктора записан в `_`, объект сразу теряется и ни на что не влияет.

```go
_, _ = NewParcel(5)   // создали и выбросили — на полке пусто
shelf := NewShelf()
_, err := shelf.Find("7") // ищем на пустой полке
```

Тест «ищу то, чего нет» бывает двух видов: в пустом хранилище и в хранилище, где лежит **другой** объект. Второй сильнее: он ловит ошибку «вернул первое попавшееся». Но для него другой объект нужно действительно положить.

В Rails это `Parcel.new(...)` без `save`: в таблице записи нет, и `Parcel.find` её не увидит.

## Что отдаёт `map`, когда ключа нет

`map` никогда не падает на чтении. Для отсутствующего ключа он отдаёт «пустое» значение того типа, который в нём лежит: `0` для числа, `""` для строки, `nil` для типа со звёздочкой.

```go
fmt.Println(stock["pear"])   // map[string]int     → 0
fmt.Println(labels["pear"])  // map[string]string  → (пустая строка)
fmt.Println(shelf["pear"])   // map[string]*Parcel → <nil>
```

Это ответ самого `map`. Метод «найти» поверх него отдаёт **два** значения: объект и ошибку. Когда ключа нет, объект — `nil`, а ошибка — не `nil`. Противоречия нет: это два разных значения.

Посмотреть на поле хранилища из теста можно напрямую: тест лежит в том же пакете, а граница видимости — пакет.

## `import cycle not allowed`: знать можно только в одну сторону

Если пакет А импортирует пакет Б, то Б импортировать А уже не может. Круг Go запрещает — код не соберётся.

```
package example.com/shop/internal/shelf
	imports example.com/shop/internal/parcel from shelf.go
	imports example.com/shop/internal/shelf from parcel.go: import cycle not allowed
```

Сообщение читается сверху вниз как цепочка: полка импортирует посылку, а посылка — полку. Круг замкнулся.

Значит, из двух пакетов только один знает о другом, и нужно выбрать кто. Полка без посылок бессмысленна, а посылке всё равно, на какой полке она лежит. Поэтому полка знает о посылке, а посылка о полке — нет.

Рядом бывает второе сообщение — `imported and not used`: импорт, которым никто не пользуется, в Go тоже ошибка.

В Ruby любой класс может сослаться на любой, и круги там обычное дело. В Go направление видно по импортам и проверяется компилятором.

## Это ещё не инверсия зависимостей

В этой задаче один пакет просто пользуется другим: хранилище импортирует домен, как `main.go` импортирует `net/http`. Инверсии здесь нет, и слова `interface` в задаче нет.
