# Конспект к задаче 01. Скелет сервиса

Здесь коротко записано всё, что ты спрашивал и что мы выяснили по ходу задачи. Примеры — на абстрактных `widgets`.

## Что такое mux

Mux (`http.ServeMux`) — это таблица маршрутов: «какой путь → какая функция его обрабатывает». Сервер получает запрос, mux смотрит на путь и вызывает нужную функцию. В Rails это `config/routes.rb`.

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /widgets", listWidgets)
```

Метод (`GET`) пишется прямо в шаблоне. Если придёт `POST`, mux сам ответит 405.

## Чем свой mux лучше глобального

`http.HandleFunc(...)` без своего mux пишет маршруты в глобальную переменную `http.DefaultServeMux` — одну на всю программу. В неё может дописать маршрут любая подключённая библиотека (мы проверяли на `net/http/pprof`: импортировал — и появился `/debug/pprof/`).

Свой mux — обычная переменная. В нём только то, что ты положил сам. Его можно передать в тест или обернуть в middleware.

## Mux — это не `app` из Rails

Mux знает только маршруты. Порт, таймауты, база, логгер — отдельные вещи. Объекта «приложение, которое знает всё» в Go нет: ты сам собираешь части в `main`.

## Что передавать в `ListenAndServe`

Второй аргумент — кому отдавать запросы.

| Где регистрируешь маршруты | Что передаёшь |
|---|---|
| `http.HandleFunc(...)` — в глобальный mux | `nil` |
| `mux.HandleFunc(...)` — в свой mux | `mux` |

Ловушка: создал свой mux, а передал `nil` — программа запустится, но на всё ответит 404.

## `ListenAndServe` не возвращается, пока сервер работает

Функция «висит», пока сервер жив. Вернётся она только когда сервер остановился, и всегда с ошибкой (порт занят, сервер закрыли). Поэтому её оборачивают в `log.Fatal`: он печатает ошибку и завершает программу с кодом 1.

Возвращается именно значение-ошибка, а не число. Код выхода 0/1 — это уже про процесс, его выставляет `log.Fatal`.

## Порядок ответа: заголовки → статус → тело

Ответ уходит клиенту в таком порядке, и вернуться назад нельзя.

```go
w.Header().Set("Content-Type", "application/json") // 1. заголовки
w.WriteHeader(http.StatusCreated)                  // 2. статус (если не 200)
w.Write(body)                                      // 3. тело
```

- `Write` сам выставляет статус 200, если его не задали. Для 200 строка с `WriteHeader` не нужна.
- После первого `Write` менять статус и заголовки бесполезно. Дописывать тело ещё одним `Write` — можно.
- Лишний `WriteHeader` видно в логе сервера: `superfluous response.WriteHeader call`.
- Если `Content-Type` не задан, Go угадывает его сам — так получался `text/plain`.

Вывод: всё, что может закончиться ошибкой, делай до первого `Write`.

## Что делать с ошибкой

«Обработать ошибку» — значит, кто-то о ней узнал.

- **До начала ответа**: лог + статус 500 клиенту + `return`.
- **После `Write`**: клиенту уже ничего не скажешь, остаётся только лог.

```go
body, err := encodeWidget(widget)
if err != nil {
	log.Printf("encode widget: %v", err)
	http.Error(w, "internal error", http.StatusInternalServerError)
	return
}

if _, err := w.Write(body); err != nil {
	log.Printf("write response: %v", err)
}
```

- `status, _ := ...` — ошибка выброшена, так не делаем.
- `if err != nil { return }` в конце функции — то же самое, что не проверять.
- `Write` падает из-за сети (клиент закрыл соединение), а не из-за преобразования в байты.

## `:=` и `=`

- `:=` — объявить новую переменную.
- `=` — присвоить уже существующей.

У `:=` слева должна быть хотя бы одна новая переменная. `_` новой не считается. Отсюда ошибка компилятора «no new variables on left side of :=».

```go
a, err := first()  // объявили a и err
_, err := second() // ошибка: нового ничего нет
_, err = second()  // правильно
```

Удобная форма, когда нужна только ошибка:

```go
if _, err := second(); err != nil {
	// err живёт только внутри этого if
}
```

## Область видимости — фигурные скобки

Переменная живёт только внутри своих `{ }`. Переменная из блока `if` не видна в блоке `else`. В Ruby область — весь метод, в Go — блок.

## Перекрытие имён (shadowing)

Если объявить переменную с именем, которое уже занято (функцией, пакетом, внешней переменной), новое имя закрывает старое до конца блока.

```go
var cfg Config
if useFile {
	cfg, err := loadConfig() // это НОВАЯ cfg, внешняя осталась пустой
	...
}
start(cfg) // пустая
```

Не называй переменные именами пакетов (`json`, `url`, `time`) и своих функций.

## Несколько условий в одном `if`

После точки с запятой — обычное условие, в нём можно `&&`.

```go
if size, ok := lookup("SIZE"); ok && size != "" {
	use(size)
}
```

## `os.Getenv` и `os.LookupEnv`

- `Getenv` возвращает пустую строку, если переменной нет. Подходит, когда «нет» и «пусто» для тебя одно и то же.
- `LookupEnv` дополнительно говорит, была ли переменная задана. Нужен, когда это важно различать.

## Как `go build` называет файл

| Команда | Имя бинарника |
|---|---|
| `go build cmd/api/main.go` (передан файл) | `main` |
| `go build ./cmd/api` или `go build ./...` (передан пакет) | `api` — по имени каталога |
| `go build -o bin/server ./cmd/api` | какое указал |

Бинарники в git не кладут. В `.gitignore` шаблон пишут со слешем в начале (`/api`), иначе он совпадёт и с каталогом `cmd/api`. Уже закоммиченный файл убирается через `git rm`.

## Зачем `r` в хендлере

`r` — запрос от клиента. Из него читают, что именно попросили. В Rails это `request` и `params`.

```go
// маршрут: "GET /widgets/{id}"
id := r.PathValue("id")
```

В `/healthz` ответ всегда одинаковый, поэтому `r` там не используется.

## Таймауты сервера

`http.ListenAndServe` запускает сервер без таймаутов: клиент может открыть соединение и молчать вечно (проверяется через `nc localhost 8080`). Много таких соединений — и сервер перестаёт отвечать. Починим на этапе 5.

## Как самому найти ответ

- `go doc http.ResponseWriter` — описание типа или функции.
- `go doc -src http.ListenAndServe` — исходный код.
- Сообщения компилятора и лог своего сервера читаются в первую очередь: в них обычно названа строка и причина.
- JSON руками не собирают — только `encoding/json`. Форматирование — только `gofmt`.
