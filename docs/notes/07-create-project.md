## Как читать панику

Полная запись — в `docs/notes/06-memory-store.md`, «Как читать панику» (уточнена во время задачи 07: четыре шага, `nil pointer dereference`, «верхняя строка — где `nil` использовали, а не где он появился»).

## После отказа проверять у объекта нечего

Если метод вернул ошибку, объекта он не вернул — там `nil`. Спрашивать у `nil` название бессмысленно: тест упадёт паникой. После ожидаемой ошибки проверяют другое: что объекта нет и что в хранилище ничего не появилось.

## `[build failed]`: тесты даже не запускались

`FAIL ... [build failed]` значит, что пакет не скомпилировался, и ни один тест в нём не выполнился. Сама причина напечатана **выше**, в начале вывода, — под строкой, которая начинается с `#` и имени пакета:

```
# example.com/shop/internal/packing [example.com/shop/internal/packing.test]
internal/packing/packing_test.go:5:2: "fmt" imported and not used
...
FAIL	example.com/shop/internal/packing [build failed]
```

Формат строки с причиной: `файл:строка:колонка: что не так`.

Если вывод длинный, удобнее запустить тесты одного пакета: `go test ./internal/packing` — тогда причина будет рядом.

Ловушка: `go build ./...` файлы `_test.go` не компилирует. Сборка может быть зелёной, а тесты — не собираться. Тесты проверяет `go vet ./...` или сам `go test`.

В Rails похоже на `SyntaxError` при загрузке spec-файла: RSpec не запустил ни одного примера.
