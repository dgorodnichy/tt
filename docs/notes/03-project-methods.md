# Конспект к задаче 03. Методы проекта

Пополняется по ходу задачи: сюда записывается всё, что ты спросил и что мы выяснили.

## Звёздочка в получателе: сам объект или копия

- `func (p *Parcel) ...` — метод работает с самим объектом. Что изменил — изменилось у вызвавшего.
- `func (p Parcel) ...` — метод получает копию. Изменения остаются в копии, а она исчезает, когда метод закончился. Компилятор при этом молчит.

```go
func (p Parcel) AddWeight(extra int) { p.weight += extra } // меняет копию — снаружи ничего не изменится
func (p *Parcel) AddWeight(extra int) { p.weight += extra } // меняет оригинал
```

Правило на сейчас: если хоть один метод типа что-то меняет — у всех методов этого типа звёздочка.

## Когда методу нужна ошибка в результате

Ошибку возвращает тот метод, у которого что-то может пойти не так. У веса посылки есть правило (не отрицательный) — метод изменения возвращает `error`. Если у поля правил нет вообще, любое значение годится, отказать нечему — и `error` в результате не нужен.

И второе: метод, о котором никто не просил, не пишем. Появится потребность — появится метод.

## Зелёные тесты проверяют только то, что в них написано

Если есть тест только на «хороший» случай, то о «плохих» ты ничего не знаешь. На каждое правило нужен тест, который пытается его нарушить. Порядок: сначала написал тест на нарушение, увидел, что он **падает**, потом чинишь код. Тест, который ни разу не падал, ничего не доказывает.

## Метод «ничего не меняет»: проверь, используется ли параметр

Внутри метода есть два похожих имени: `p.weight` — то, что лежит в объекте **сейчас**, и параметр `weight` — то, что **прислали**. Перепутать легко, и компилятор не подскажет: неиспользуемый параметр функции ошибкой не считается (в отличие от неиспользуемой переменной).

```go
func (p *Parcel) SetWeight(weight int) {
	p.weight = p.weight // записали старое в старое; параметр weight забыт
}
```

Первое, что стоит сделать, когда метод «не работает»: найти в его теле каждое место, где встречается параметр. Если ни одного — причина найдена.

Отладка через `fmt.Println` до и после вызова — нормальный способ. После него вывод убирают, а проверку записывают в тест через `if` и `t.Errorf`.

## Что говорит компилятор про закрытое поле

Обращение к полю с маленькой буквы из другого пакета:

```
p.weight undefined (type *store.Parcel has no field or method weight, but does have method Weight)
```

Для чужого пакета такого поля как будто не существует — `undefined`. Компилятор при этом сам подсказывает, что есть метод с похожим именем. Сообщения Go стоит дочитывать до конца: во второй половине часто лежит ответ.

Граница видимости — пакет: внутри своего каталога поле доступно всем файлам (и тестам), снаружи — никому.

## Как импортировать свой пакет

Путь в `import` — это **имя модуля из `go.mod`** плюс **путь до каталога** внутри проекта. Относительных путей (`./internal/...`) в импортах нет.

Если в `go.mod` написано `module example.com/shop`, а пакет лежит в `internal/store`:

```go
import "example.com/shop/internal/store"

// дальше в коде
store.NewParcel(5)
```

Путь без имени модуля в начале Go принимает за пакет стандартной библиотеки (как `net/http`) и отвечает `package ... is not in std`. Это та же ошибка, что была с `go test internal/...` во второй задаче, — причина одна.

Имя перед путём (`store "example.com/shop/internal/store"`) писать не нужно: Go сам берёт имя из строки `package store`. Его пишут, только когда два пакета называются одинаково.

В Ruby `require` ищет файл по путям загрузки. В Go путь всегда полный и начинается с имени модуля.
