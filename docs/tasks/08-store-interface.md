# Задача 08. Интерфейс хранилища

Этап 2. Задача маленькая. Одна новая тема Go: **интерфейс**.

## Зачем

Ты сам ответил в задаче 07: сценарий не должен ничего знать о `memory`. Сейчас знает — `go list -f '{{.Imports}}' ./internal/usecase` показывает его в импортах.

Почему это плохо. Хранилище в памяти — временное, потом придёт SQLite. Если сценарий держит в поле именно `*memory.Repo`, то при переходе на базу придётся переписывать сценарий, хотя правила создания проекта не поменялись.

Сценарию на самом деле неважно, **что** у него в поле. Ему важно одно: у этой штуки есть метод «сохранить». Вот это «у неё есть такой метод» в Go и записывают интерфейсом.

## На что это похоже

В Ruby это утиная типизация: метод вызывает `shelf.put(parcel)` и не спрашивает, какого класса `shelf`. Есть `put` — годится.

Интерфейс в Go — то же самое, только список нужных методов записан явно, и компилятор проверяет его заранее, а не во время работы.

Главное отличие от Ruby-модулей и от `implements` в Java: **тип нигде не пишет, что подходит под интерфейс.** Если у типа есть нужные методы — он подходит, сам по себе.

## Что сделать

1. В пакете `usecase` объяви интерфейс с одним методом — тем, которым сценарий пользуется. Сигнатура метода — как у твоего хранилища. Имя интерфейса — твоё.
2. Поле сценария и параметр его конструктора — этого интерфейсного типа, а не `*memory.Repo`.
3. Импорт `memory` из `create_project.go` уходит.
4. Тесты не меняются: они по-прежнему создают `memory.NewRepo()` и отдают его в конструктор сценария.

Двигайся по шагам: объявил интерфейс → поменял поле и параметр → запустил `go build ./...` и `go test ./...`.

## Критерии приёмки

- `go test ./...` проходит, три теста сценария те же и зелёные.
- `go list -f '{{.Imports}}' ./internal/usecase` показывает только `domain`. (Импорты из файлов `_test.go` эта команда не показывает: тестам знать о `memory` можно — они собирают всё вместе, как `main`.)
- Интерфейс объявлен в пакете `usecase`, а не в `memory`. Причина: список нужных методов знает тот, кто ими пользуется. Хранилище не знает, кто и зачем его позовёт.
- В интерфейсе один метод. Причина: сценарий вызывает только «сохранить». Метод «найти» ему не нужен, и требовать его — значит требовать от любого будущего хранилища лишнего.
- Пакет `memory` не изменён: `git diff` по нему пуст. Он подходит под интерфейс сам, без единой правки.
- `internal/domain` и `cmd/api/main.go` не изменены.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый.

## Приём на абстрактном примере

Упаковщику нужна не полка, а «что-нибудь, куда можно положить посылку»:

```go
type ParcelKeeper interface {
	Put(p *Parcel)
}

type Packer struct {
	keeper ParcelKeeper
}

func NewPacker(keeper ParcelKeeper) *Packer {
	return &Packer{keeper: keeper}
}
```

Собирают так же, как раньше:

```go
shelf := store.NewShelf()
packer := NewPacker(shelf) // у *Shelf есть Put(p *Parcel) — подходит
```

У `Shelf` нигде не написано «я `ParcelKeeper`». Компилятор сам сверил методы.

## Мостики из Ruby

- `respond_to?(:put)` — то, что компилятор Go проверяет за тебя в момент сборки.
- В Ruby ошибка «нет такого метода» всплывёт во время работы (`NoMethodError`). В Go — при сборке, с сообщением, какого метода не хватает.
- `include Keepable` в Ruby — объявление на стороне класса. В Go такого объявления нет вообще.
