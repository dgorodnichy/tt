# Задача 02. Доменная сущность «проект»

Этап 1. Одна новая тема: **объект, который нельзя создать неправильным**. Без HTTP, без базы, без сторонних библиотек.

По времени не ориентируйся на часы — задача рассчитана на несколько коротких подходов.

## Цель

Описать проект как тип и дать единственный способ его создать — функцию-конструктор, которая либо возвращает корректный проект, либо ошибку. Проверить это тестом.

## Что сделать

1. Создать пакет `internal/domain`. Код — в `project.go`, тест — в `project_test.go` рядом.
2. Описать тип проекта с двумя полями: название и описание.
3. Написать конструктор, который принимает название и описание и возвращает проект и ошибку.
4. Правила для названия:
   - пробелы по краям отбрасываются;
   - после этого оно не может быть пустым;
   - длина — не больше 100 символов.
5. На каждое нарушение — своя ошибка, объявленная в пакете как переменная (чтобы вызывающий код мог отличить одну от другой).
6. Описание необязательное, правил для него нет.
7. Написать тесты на конструктор средствами стандартного пакета `testing`.

`cmd/api/main.go` в этой задаче не трогаем: домен пока никто не использует, и это нормально.

## Критерии приёмки

- `go test ./...` проходит.
- Тесты покрывают минимум пять случаев: корректное название; пустая строка; строка из одних пробелов; название с пробелами по краям (проверяется, что они отброшены); слишком длинное название.
- Название из 100 русских букв — допустимо, из 101 — нет. На это есть тест.
- В тестах ошибка сравнивается через `errors.Is`, а не по тексту.
- При ошибке конструктор не возвращает наполовину заполненный проект.
- `go list -f '{{.Imports}}' ./internal/domain` показывает только стандартную библиотеку, и в списке нет `net/http`, `encoding/json`, `database/sql`.
- У полей типа нет тегов `json:"..."`.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` перед коммитом не показывает лишнего.

## Как проверять себя по ходу

Здесь нет сервера и `curl` — единственный способ узнать, работает ли код, это тест. Поэтому порядок такой: написал правило → написал на него тест → `go test ./...` → следующее правило. Не оставляй тесты на конец.

Полезные формы запуска: `go test ./... -v` (показать имена тестов), `go test ./internal/domain -run ИмяТеста`.

## Что изучить

- Структуры: объявление, создание значения, zero value. `go doc` тут не поможет — смотри tour.golang.org, раздел «Structs», и gobyexample.com/structs.
- Конструкторы в Go: почему это обычная функция `NewЧтоТо`, а не особый синтаксис. Effective Go, раздел «Constructors and composite literals».
- Ошибки-переменные: `go doc errors.New`, `go doc errors.Is`.
- Тесты: `go doc testing` (первые два экрана), gobyexample.com/testing-and-benchmarking. Разница между `t.Errorf` и `t.Fatalf`.
- Строки: `go doc strings.TrimSpace`. И отдельно — выполни в playground `len("привет")` и объясни результат, прежде чем писать проверку длины. Подсказка, куда смотреть дальше: `go doc unicode/utf8`.
- Каталог `internal/`: что компилятор запрещает делать с пакетами внутри него.

## Приём на абстрактном примере

```go
var ErrNegativeWeight = errors.New("weight must not be negative")

type Parcel struct {
	Weight int
}

func NewParcel(weight int) (Parcel, error) {
	if weight < 0 {
		return Parcel{}, ErrNegativeWeight
	}
	return Parcel{Weight: weight}, nil
}
```

```go
func TestNewParcelRejectsNegativeWeight(t *testing.T) {
	_, err := NewParcel(-1)
	if !errors.Is(err, ErrNegativeWeight) {
		t.Fatalf("got error %v, want %v", err, ErrNegativeWeight)
	}
}
```

Это показывает форму. Какие поля, имена и проверки нужны тебе — решаешь сам.

## Мостики из Ruby

- В Rails объект сначала создаётся, а потом спрашивается `valid?` — невалидный объект может жить в памяти и гулять по коду. Здесь наоборот: если у тебя на руках есть проект, он уже корректен. Проверять его повторно нигде не придётся.
- Вместо `raise ArgumentError` в `initialize` — второе возвращаемое значение. Вызывающий код обязан что-то с ним сделать прямо на месте.
- Вместо `describe`/`it` — обычные функции `TestЧтоТо(t *testing.T)`. Вместо `expect(...).to eq` — обычный `if` и `t.Errorf`. Никакого DSL.
- Тест лежит рядом с кодом в том же каталоге, а не в отдельном `spec/`.
- В `domain` нет ничего от фреймворка: ни `ApplicationRecord`, ни сериализации, ни колбэков. Это не модель ActiveRecord, а чистые данные и правила.

## Вопросы для самопроверки (ответь при сдаче, коротко)

Каждый привязан к твоему коду.

1. Покажи строку, где ты объявил ошибки. Почему тест сравнивает их через `errors.Is`, а не `err.Error() == "текст"`? Что сломается при втором способе, если ты поправишь опечатку в тексте ошибки?
2. Опыт: в тесте создай проект в обход конструктора — литералом, с пустым названием. Компилируется? Что это значит для обещания «проект всегда корректен» и как Go позволяет закрыть эту дыру? (Закрывать пока не надо — только ответить.)
3. Опыт: добавь в `project.go` импорт `net/http` и используй что-нибудь оттуда. Компилятор возражает? Тогда кто и как следит за тем, что домен не зависит от HTTP?
4. Почему у проекта пока нет ни `ID`, ни даты создания? Попробуй предположить, какие вопросы пришлось бы решить, чтобы их добавить.

## Чего не делать

- Не добавлять `ID`, даты, владельца, статус — появятся в следующих задачах.
- Не подключать `testify` и `validator` — сначала нужно почувствовать, что они заменяют.
- Не писать методы изменения проекта (переименование и т. п.).
- Не создавать другие каталоги внутри `internal/`.
