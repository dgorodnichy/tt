# Задача 09. Сценарий «найти проект»

Этап 2. Задача маленькая. Новой темы Go нет. Одна новая мысль: **у каждого потребителя — свой интерфейс**.

## Зачем

Проект можно создать через сценарий, а найти — пока только напрямую через хранилище. Добавим второй сценарий: «найти проект по идентификатору».

Ему от хранилища нужно другое, чем первому: не «сохранить», а «найти». И по правилу из задачи 08 — интерфейс содержит только то, чем потребитель пользуется.

## На что это похоже

Форма та же, что у сценария «создать проект» из задач 07–08: интерфейс в один метод → тип с полем этого интерфейса → конструктор → один метод.

| | Создать проект (07–08) | Найти проект (09) |
|---|---|---|
| интерфейс | один метод — «сохранить» | один метод — «найти» |
| поле | хранилище через интерфейс | хранилище через свой интерфейс |
| метод сценария | создать и сохранить | найти и вернуть |

Новое одно: **одно и то же хранилище подходит под оба интерфейса сразу.** У него есть оба метода, а каждый сценарий видит в нём только свой.

## Что сделать

1. В пакете `usecase`, в новом файле, — интерфейс с одним методом «найти». Сигнатура — как у твоего хранилища. Имя — твоё.
2. Тип-сценарий с полем этого интерфейса, конструктор, один метод «найти»: принимает идентификатор, возвращает проект и ошибку.
3. Если хранилище вернуло ошибку — сценарий возвращает её как получил. Как в задаче 07 с ошибкой домена.
4. Тесты.

## Критерии приёмки

- `go test ./...` проходит.
- Тесты нового сценария покрывают два случая:
  - проект создан **сценарием «создать проект»**, найден **сценарием «найти проект»**, и оба сценария получили **одно и то же** хранилище — название и описание совпадают;
  - идентификатора нет — ошибка «не найдено» (через `errors.Is`), проекта нет.
- У каждого сценария свой интерфейс, в каждом один метод. Причина: если сценарию «создать» потребовать и «найти», то любое будущее хранилище, которому нужно только сохранять, придётся дописывать ради метода, которым никто не пользуется.
- Сценарий «найти» не меняет ошибку хранилища.
- `go list -f '{{.Imports}}' ./internal/usecase` — по-прежнему только `domain`.
- В файлах сценария «создать проект» разрешено только переименование — по правилам имён из `docs/drills/01-interfaces.md` (интерфейс — по умению, поле — по роли). Логика не меняется. Пакеты `memory`, `domain` и `cmd/api/main.go` не изменены.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый, опыты убраны.

## Что изучить

Новой темы нет. Перечитай свой конспект `docs/notes/08-store-interface.md` — «В каком файле объявлять интерфейс» и «Где компилятор ругается, если тип не подходит под интерфейс».

## Приём на абстрактном примере

Одна полка, два разных потребителя:

```go
type ParcelKeeper interface {
	Put(p *Parcel)
}

type ParcelFinder interface {
	Find(code string) (*Parcel, error)
}
```

```go
shelf := store.NewShelf()
packer := NewPacker(shelf)   // видит в полке только Put
courier := NewCourier(shelf) // видит в полке только Find
```

Полка одна. Упакованное упаковщиком курьер найдёт, потому что оба держат одну и ту же полку.

## Мостики из Ruby

- В Ruby обоим сервис-объектам отдали бы один и тот же объект, и каждый вызывал бы свой метод. Здесь то же самое, только каждый ещё и записал, какой метод ему нужен.
- `rescue => e; raise e` — бессмысленная обёртка. Вернуть ошибку как есть в Go — `return nil, err`.
