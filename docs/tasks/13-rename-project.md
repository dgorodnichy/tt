# Задача 13. Сценарий «переименовать проект»

Этап 2, последняя задача этапа. Новой темы Go нет. Одна новая мысль: **интерфейсу можно дать два метода, если сценарий пользуется обоими.** Правило всегда было «только то, что вызываешь», а не «всегда один метод».

## Зачем

У проекта есть `SetName` (задача 03), но сценария для него нет. Переименование — первый сценарий, который делает больше одного шага: найти → изменить → сохранить.

## На что это похоже

| | Создать (07) | Найти (09) | Переименовать (13) |
|---|---|---|---|
| что вызывает у хранилища | `Add` | `Get` | `Get`, потом `Add` |
| интерфейс | один метод | один метод | **два метода** |
| что вызывает у домена | `NewProject` | — | `SetName` |
| ошибки | домена — как есть | хранилища — как есть | обе — как есть |

Форма — те же четыре блока. Образец — `create_project.go` и `get_project.go`, открывай рядом.

## Перед кодом — три вопроса

Ответь словами до кода и приложи при сдаче (вопрос 1 самопроверки):

1. Что сценарий вызывает у хранилища?
2. Захочу ли я подменить хранилище?
3. Значит, какой интерфейс и где он стоит?

## Что сделать

1. В `usecase`, в новом файле, — интерфейс с двумя методами, сценарий, конструктор, `Call(id, name)`.
2. `Call`: находит проект, меняет ему название через `SetName`, сохраняет через `Add`. Возвращает переименованный проект и ошибку.
3. Если проекта нет — ошибка хранилища как есть, `SetName` и `Add` не вызываются.
4. Если `SetName` отказал — ошибка домена как есть, `Add` не вызывается.
5. Тесты:
   - на настоящем хранилище: создал сценарием «создать», переименовал, сценарий «найти» видит новое название;
   - на настоящем хранилище: id нет → «не найдено» через `errors.Is`;
   - с фейком: пустое новое название → ошибка домена через `errors.Is` **и** `Add` вызван 0 раз;
   - с фейком: всё верно → `Add` вызван 1 раз.

Фейк под этот интерфейс должен уметь оба метода: `Get` отдаёт заранее положенный проект, `Add` считает вызовы.

## Критерии приёмки

- `go test ./...` проходит, все старые тесты на месте.
- Четыре теста из списка выше.
- В интерфейсе ровно два метода — те, что сценарий вызывает. `Adder`, `Getter`, `Fetcher`, `Remover` не меняются.
- Ошибки хранилища и домена возвращаются как есть.
- `go list -f '{{.Imports}}' ./internal/usecase` — только `domain`.
- Фейк — в `_test.go`.
- `memory`, `internal/domain`, `cmd/api/main.go` и файлы прошлых сценариев не изменены.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый, опыты убраны.

## Приём на абстрактном примере

Интерфейс из двух методов пишется так же, как из одного:

```go
type ShelfKeeper interface {
	Get(code string) (*Book, error)
	Put(b *Book)
}
```

Тип подходит под него, если у него есть **оба** метода. У `memory`-полки есть оба — подходит без правок.

## Мостики из Ruby

- В Rails это `project = Project.find(id); project.update!(name: ...)`. Здесь три явных шага: найти, изменить сущность, сохранить.
- `update!` бросает исключение — здесь каждая ошибка возвращается значением, и после ошибки сценарий дальше не идёт.
