# Задача 05. Идентификатор проекта

Переход от этапа 1 к этапу 2. Нового синтаксиса Go здесь почти нет. Тема задачи: **откуда у объекта берётся идентификатор**, и как менять сигнатуру функции, когда на неё уже есть тесты.

Задача короткая.

## Зачем

Сейчас два проекта с названием `Site` ничем не отличаются. Скоро проекты нужно будет где-то хранить и доставать обратно: «дай мне вот этот проект». Для слова «этот» нужен идентификатор.

В Rails идентификатор выдаёт база в момент `save`: до сохранения `id` равен `nil`. Здесь по-другому: проект получает идентификатор **при создании**, от того, кто его создаёт. Так объект с первой секунды полный, и базе для этого существовать не нужно.

## Хвост с задачи 04 закрыт

Проверка описания в тесте конструктора уже добавлена. Остаётся убедиться опытом, что она ловит ошибку, — это вопрос 2.

## Что сделать

1. У проекта появляется идентификатор — строка.
2. Конструктор принимает его первым параметром.
3. Правило одно: идентификатор не пустой. На нарушение — своя ошибка-переменная, как для названия.
4. Метод для чтения идентификатора. Метода для изменения нет: идентификатор не меняется никогда.
5. Тесты: в таблицу конструктора добавить случаи про идентификатор. Тест переименования должен продолжать работать.

Двигайся так: сначала поменяй конструктор и сразу запусти `go test ./...`, ничего не исправляя в тестах. Прочитай, что скажет компилятор, — это вопрос 1.

## Критерии приёмки

- `go test ./...` проходит.
- В выводе `go test ./internal/domain -v` есть случай с пустым идентификатором и случай, где идентификатор проверяется после успешного создания.
- Ошибка пустого идентификатора — отдельная переменная, проверяется через `errors.Is`.
- Метод чтения назван так, как принято в Go для сокращений (см. «Что изучить»).
- Описание проверяется в тесте конструктора.
- В `project.go` нет способа поменять идентификатор снаружи пакета.
- `/healthz` по-прежнему отвечает `{"status":"ok"}`, `cmd/api/main.go` не изменён.
- `go list -f '{{.Imports}}' ./internal/domain` — только стандартная библиотека.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый.

## Приём на абстрактном примере

У посылки появляется код, который выдаёт отправитель:

```go
var ErrBlankCode = errors.New("blank code")

func NewParcel(code string, weight int) (*Parcel, error) {
	if code == "" {
		return nil, ErrBlankCode
	}
	// ... остальные проверки, как раньше
}
```

Когда у функции меняется список параметров, компилятор сам покажет каждое место, где её вызывают по-старому. Искать их глазами не нужно.

## Мостики из Ruby

- В Rails: `Parcel.new(weight: 5).id # => nil`, идентификатор появится после `save`. Здесь объекта без идентификатора не бывает.
- В Ruby после смены параметров метода старые вызовы падают по одному, когда до них дойдёт выполнение. В Go они все не соберутся сразу.
- `attr_reader :id` без `attr_writer` — это и есть «метод чтения есть, метода изменения нет».

## Вопросы для самопроверки (ответь при сдаче, коротко)

1. Ты поменял конструктор и запустил тесты, ничего в них не исправляя. Приведи сообщение компилятора дословно. На сколько мест он указал?
2. Опыт: временно сделай так, чтобы конструктор сохранял вместо описания пустую строку. Запусти тесты и приведи строку с `FAIL`. Верни как было. Если ничего не упало — проверка описания не работает.
3. Приведи команду, которой запускается один случай с пустым идентификатором, и её вывод.
4. Своими словами, одно-два предложения: в какой момент появляется `id` у записи в Rails и в какой — у проекта здесь?

## Чего не делать

- Не генерировать идентификаторы (никаких `uuid` и счётчиков): в тестах это просто строка вроде `"p1"`.
- Не заводить для идентификатора отдельный тип.
- Не обрезать пробелы в идентификаторе и не придумывать ему других правил.
- Не делать хранилище — оно в следующей задаче.
