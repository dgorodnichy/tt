# Задача 03. Методы проекта

Этап 1, продолжение. Одна новая тема: **методы** — функции, привязанные к типу.

По времени не ориентируйся на часы — несколько коротких подходов.

## Зачем

В задаче 02 ты спрятал поля проекта: они с маленькой буквы. Это правильно, но теперь другой пакет не может даже прочитать название. А переименовать проект нельзя вообще никому — либо в обход правил, либо никак.

Нужны две вещи: способ прочитать поля и способ изменить название так, чтобы правила из конструктора продолжали работать.

## Что сделать

1. Добавить проекту методы для чтения названия и описания.
2. Добавить метод переименования. Он принимает новое название и возвращает ошибку.
3. Правила для нового названия — те же, что в конструкторе: пробелы по краям отбрасываются, не пустое, не больше 100 символов. Ошибки — те же переменные.
4. Правила должны быть записаны в коде один раз. И конструктор, и переименование пользуются одним и тем же местом.
5. Если новое название не прошло проверку, старое остаётся как было.
6. Написать тесты на переименование.
7. Хвост с прошлой задачи: `project_test.go:68`.

Работаем по-прежнему в `internal/domain`, новых каталогов нет. `cmd/api/main.go` меняется только на время опыта из вопроса 2.

## Критерии приёмки

- `go test ./...` проходит.
- Методы чтения названы так, как принято в Go (см. «Что изучить», Effective Go).
- Тесты на переименование: корректное название (изменилось и обрезано); пустое; слишком длинное. В двух последних проверяется и ошибка через `errors.Is`, и то, что название осталось прежним.
- В тестах поля читаются через новые методы, а не напрямую.
- Проверки названия в `project.go` не повторяются: условие «пустое» и условие «длиннее 100» встречаются в файле по одному разу.
- Там, где после ошибки продолжать тест нет смысла, стоит `Fatalf`.
- `go list -f '{{.Imports}}' ./internal/domain` — только стандартная библиотека.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` перед коммитом не показывает лишнего.

## Как проверять себя по ходу

Как и раньше: написал кусок → написал тест → `go test ./internal/domain -v`. Начни с методов чтения, потом вынеси правила в одно место (тесты из задачи 02 должны остаться зелёными — они скажут, что ты ничего не сломал), и только потом переименование.

## Приём на абстрактном примере

Метод — это обычная функция, у которой перед именем в скобках написано, к какому типу она относится. Эта часть в скобках называется получателем (receiver).

```go
type Parcel struct {
	weight int
}

// метод чтения
func (p *Parcel) Weight() int {
	return p.weight
}

// метод изменения
func (p *Parcel) AddWeight(extra int) error {
	if extra < 0 {
		return ErrNegativeWeight
	}
	p.weight = p.weight + extra
	return nil
}
```

Вызов:

```go
parcel, err := NewParcel(5)
// ...
err = parcel.AddWeight(3)
fmt.Println(parcel.Weight()) // 8
```

### Про звёздочку в получателе

Это единственное новое место, где нужно быть внимательным.

- `func (p *Parcel) ...` — метод работает с **самой** посылкой. Изменил вес — он изменился у того, кто метод вызвал.
- `func (p Parcel) ...` — метод получает **копию** посылки. Изменил вес у копии — оригинал остался прежним, и компилятор при этом молчит.

В Ruby такого выбора нет: метод всегда работает с самим объектом. В Go ты выбираешь явно. Простое правило на сейчас: если хотя бы один метод типа что-то меняет — у всех методов этого типа пишем звёздочку.

Почему так устроено, ты увидишь сам в вопросе 1.

## Мостики из Ruby

- Метод чтения — это `attr_reader`, только написанный руками. `attr_accessor` в Go не делают: запись идёт через метод с проверкой, как `AddWeight` выше.
- Получатель `p` — это `self`, только у него есть имя и ты выбираешь его сам. Обычно это первая буква типа.
- Методы не лежат внутри `class ... end`. Они пишутся отдельными функциями рядом с типом, в том же пакете.
- Вместо `rename!` с исключением — метод, который возвращает ошибку.

1. Опыт: когда тесты на переименование станут зелёными, убери звёздочку в получателе метода переименования и запусти тесты. Что упало и какое сообщение? Объясни своими словами, куда делось новое название. Верни звёздочку.
2. Опыт: в `cmd/api/main.go` временно создай проект через конструктор и попробуй напечатать его название, обратившись к полю напрямую. Прочитай сообщение компилятора и приведи его. Потом напечатай через метод. Что это говорит о том, откуда видны поля с маленькой буквы? Верни `main.go` как был (`git diff` должен быть пустым).
3. Покажи строку, где записано правило «не больше 100». Что случилось бы через полгода, если бы оно было записано отдельно в конструкторе и отдельно в переименовании?
4. Почему для описания ты не писал метод изменения? (Подсказка: посмотри в раздел «Что сделать».) А если бы понадобился — нужна ли ему была бы ошибка в результате?
