# Задача 07. Сценарий «создать проект»

Этап 2. Задача намеренно маленькая. Одна новая мысль: **объект, который пользуется другим объектом**.

## Зачем

Сейчас, чтобы проект появился в хранилище, нужно сделать два шага руками: создать его конструктором и положить в хранилище. В тестах задачи 06 ты повторил эти два шага четыре раза.

Соберём их в одно место. Это место называется сценарий: «создать проект» = проверить и создать → сохранить. Позже этот сценарий будет вызывать HTTP-обработчик.

В Rails это сервис-объект: `CreateParcel.new(shelf).call(...)`.

## На что это похоже

Форма та же, что в задачах 02–03 и 06: **тип с закрытым полем → конструктор → метод**.

| | Проект (02–03) | Хранилище (06) | Сценарий (07) |
|---|---|---|---|
| закрытое поле | строка | `map` | хранилище |
| конструктор | проверяет и заполняет | создаёт пустой `map` | принимает готовое хранилище и кладёт в поле |
| методы | прочитать, сменить название | сохранить, найти | создать проект |

Новое одно: в поле лежит не строка и не `map`, а твой собственный объект из другого пакета. И конструктор его не создаёт, а получает снаружи.

## Что сделать

1. Новый каталог `internal/usecase`, пакет `usecase`. Файл назови по содержимому, тесты — рядом, с `_test.go` на конце.
2. В нём тип-сценарий. Внутри одно закрытое поле — хранилище из пакета `memory`.
3. Конструктор сценария: принимает хранилище, возвращает сценарий.
4. Один метод «создать». Принимает идентификатор, название и описание. Внутри три шага:
   - создать проект конструктором домена;
   - если конструктор отказал — вернуть его ошибку как есть, ничего не сохранять;
   - иначе сохранить проект в хранилище и вернуть его.
5. Тесты.

Двигайся по одному шагу: тип и конструктор → соберётся ли → метод → первый тест → остальные.

Пути импорта пиши полностью, до каталога пакета. Образец — `internal/adapter/memory/map.go:6`, запись в `docs/notes/03-project-methods.md`: «Как импортировать свой пакет».

## Критерии приёмки

- `go test ./...` проходит, в выводе три пакета с тестами.
- Тесты сценария покрывают три случая:
  - создал проект — метод вернул проект с тем же названием, и этот проект находится в хранилище по идентификатору;
  - пустое название — ошибка «пустое название» из домена (через `errors.Is`), и в хранилище по этому идентификатору ничего нет;
  - пустой идентификатор — ошибка «пустой идентификатор» из домена.
- Сообщения тестов — в виде «got …, want …».
- Сценарий не создаёт хранилище сам: в пакете `usecase` нет вызова конструктора хранилища (кроме тестов). Причина: хранилище одно на всю программу, и им будут пользоваться другие сценарии. Если каждый создаст своё, они не увидят проекты друг друга.
- Сценарий не меняет ошибку домена: возвращает её как получил. Причина: тот, кто вызвал сценарий, должен суметь узнать её через `errors.Is`.
- В пакете `usecase` один метод. «Найти», «удалить», «список» появятся, когда понадобятся.
- В пакете нет слова `interface`. Он появится в следующей задаче, и ты увидишь зачем.
- `internal/domain` и `internal/adapter/memory` не изменены.
- `cmd/api/main.go` не изменён.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый.

## Приём на абстрактном примере

Упаковщик пользуется полкой. Полку ему дают при создании:

```go
type Packer struct {
	shelf *Shelf
}

func NewPacker(shelf *Shelf) *Packer {
	return &Packer{shelf: shelf}
}
```

Собирают их так — сначала полка, потом упаковщик, которому её отдали:

```go
shelf := NewShelf()
packer := NewPacker(shelf)
```

Метод упаковщика достаёт полку через получатель, как любое другое поле: `p.shelf`. А дальше вызывает её методы.

## Мостики из Ruby

- Это сервис-объект: `initialize(shelf)` запоминает `@shelf = shelf`, метод `call` делает работу.
- `Parcel.create(...)` в Rails прячет оба шага внутри модели. Здесь шаги те же, но лежат в отдельном объекте — сценарии. Модель про хранилище не знает.
- Ошибку конструктора ты не ловишь и не заворачиваешь: `return nil, err`. В Ruby это как не писать `rescue` — исключение само уйдёт наверх. В Go «наверх» пишут руками.
