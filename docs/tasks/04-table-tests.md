# Задача 04. Табличные тесты

Этап 1, завершение. Одна новая тема: **табличные тесты** (table-driven tests) — главный способ писать тесты в Go.

Код в `project.go` в этой задаче не меняется. Меняются только тесты.

## Зачем

Открой `project_test.go` и сравни `TestNewProjectBlankName` и `TestNewProjectSpacesName`. Они отличаются одной строкой — входным названием. То же самое с парой «100 букв / 101 буква» и с тремя тестами на переименование, где четыре строки создания проекта повторяются слово в слово.

Сейчас в файле 11 функций и больше ста строк. Чтобы добавить ещё один случай, нужно скопировать функцию целиком. В Go так не делают: случаи записывают таблицей, а проверку пишут один раз.

## Сначала хвост с задачи 03

В `cmd/api/main.go` остался код опыта: импорт домена, создание проекта `foo` и поле `name` в ответе `/healthz`. Убери эти три места, чтобы `/healthz` снова отвечал только `{"status":"ok"}`. Проверь через `curl`, закоммить отдельным коммитом.

## Что сделать

1. Переписать тесты конструктора в один табличный тест. В таблицу попадают все случаи, которые сейчас разнесены по функциям: обычное название, пробелы по краям, пустое, одни пробелы, 100 русских букв, 101 русская буква, 101 латинская.
2. У каждого случая в таблице есть своё имя, и оно видно в выводе `go test -v`.
3. Так же переписать тесты переименования — во вторую таблицу.
4. Старые отдельные функции, которые стали строками таблиц, удалить.

Двигайся по одному шагу: сначала таблица из двух случаев конструктора, запустил, увидел зелёное — добавляешь остальные и только потом удаляешь старые функции.

## Критерии приёмки

- `go test ./...` проходит.
- В `project_test.go` две тестовые функции с таблицами: на конструктор и на переименование. (Если что-то не ложится в таблицу — можно оставить отдельной функцией, но объясни при сдаче, почему.)
- Ни один случай из старых тестов не потерян.
- `go test ./internal/domain -v` показывает каждый случай отдельной строкой с понятным именем.
- Один случай можно запустить отдельно через `-run`.
- Ошибки сравниваются через `errors.Is`.
- Сообщения при падении — в формате «got …, want …»: по сообщению видно, что пришло и что ожидалось.
- После неудачного создания проекта тест не идёт дальше (`Fatal`).
- `project.go` не изменён: `git diff` по нему пуст.
- `go vet ./...` чист, `gofmt -l .` пуст, `git status` чистый.

## Приём на абстрактном примере

```go
func TestNewParcel(t *testing.T) {
	tests := []struct {
		name       string
		weight     int
		wantWeight int
		wantErr    error
	}{
		{name: "обычный вес", weight: 5, wantWeight: 5, wantErr: nil},
		{name: "нулевой вес", weight: 0, wantWeight: 0, wantErr: nil},
		{name: "отрицательный вес", weight: -1, wantErr: ErrNegativeWeight},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := NewParcel(tt.weight)

			if !errors.Is(err, tt.wantErr) {
				t.Fatalf("got error %v, want %v", err, tt.wantErr)
			}
			if tt.wantErr != nil {
				return // ждали ошибку и получили её — проверять больше нечего
			}
			if got.Weight() != tt.wantWeight {
				t.Errorf("got weight %d, want %d", got.Weight(), tt.wantWeight)
			}
		})
	}
}
```

Как это читать:

- `tests` — список случаев. Каждый случай — маленькая структура: имя, что подаём, что ждём.
- `for _, tt := range tests` — пройти по списку. `tt` — очередной случай.
- `t.Run(имя, функция)` — запустить случай как отдельный маленький тест со своим именем.

Какие поля нужны в твоих таблицах — решаешь сам, они будут другими.

## Мостики из Ruby

- Это то же, что в RSpec пишут так:

  ```ruby
  [[5, 5], [0, 0]].each do |weight, expected|
    it "accepts #{weight}" do ... end
  end
  ```

  Только в Go это не приём для особых случаев, а обычный вид теста.
- `t.Run("имя", ...)` — это `it "имя" do ... end`.
- Имена полей в таблице заменяют комментарии: `{name: ..., weight: ..., wantErr: ...}` читается без пояснений.
